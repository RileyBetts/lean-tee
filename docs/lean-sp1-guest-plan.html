Plan: Compiled Lean → C → RISC-V on SP1 (no Rust twin)

Decision (locked)

  • **Stay on SP1** because of the Lean-oriented prover formalization track ([sp1-lean](https://github.com/succinctlabs/sp1-lean) / Sail), not because Rust is the guest language of record.
  • **Do not pursue the Rust twin as the proven semantic guest.** Rust may remain only as:

    • - host Prove/adapters (prove_server, lean_tee_receipt), and

    - a thin zkVM I/O shim (read public inputs / commit outputs) if required by sp1-zkvm.

    • **Proven guest body** = Lean-compiled C lowered with the SP1 RISC-V toolchain to a measured ELF.
    • **Full Lean kernel in-guest** = stretch goal only after a working restricted guest.

    Scope of Lean that runs in SP1 (phase 1)

    In scope (pure, first-order, bounded):

    • `LeanTee.Guest` decision oracle (allow/deny + reason digest inputs as today).
    • `LeanTee.GuestProg.parse` / `run` / `runBytes` for v1/v2 program bytes.
    • SHA-256 via existing Lean FFI **only if** OpenSSL (or a pure Lean/C sha256) can be linked into SP1; otherwise a **small C sha256** used by both Lean `@[extern]` and documented as part of guest TCB (prefer one shared C sha256 used by Lean FFI on host *and* guest for parity).

    Out of scope for phase 1:

    • `teeServer`, lean-grpc, `IO` networking, filesystem, threads, Lean elaborator, mathlib, full `Init` surface.
    • Uploading arbitrary Lean source at runtime (still not a goal).
    • Proving the SP1 chips in-tree (consume upstream `sp1-lean` as dependency/docs later; do not block guest work on finishing chip proofs).

    Stretch (later): grow Init/runtime toward more of the Lean runtime (“kernel-like” capabilities). Explicit non-goal until phase 1 ELF proves + verifies for compliance + GuestProg.

    ABI (normative for the Lean entry)

    Match today’s SP1 guest public interface so receipts stay compatible:

    read:  config_hash : [u8;32]
read:  inputs      : bytes
read:  program     : bytes   -- empty => compliance path; non-empty => GuestProg
commit: outputs    : bytes   -- decision=…\nreason=…

    Lean exports a single C-callable entry, e.g.:

    // lean_tee_guest_run(config_hash, config_hash_len,
//                    inputs, inputs_len,
//                    program, program_len,
//                    /* out */ uint8_t** outputs, size_t* outputs_len) -> int

    Semantics must equal current Lean GuestProg.run_measured / compliance run (byte-identical outputs for goldens).

    Workstreams

    A. Lean guest library (spec-executable slice)

    1. Create `LeanTee/GuestSp1.lean` (name flexible) that depends only on Hash/Guest/GuestProg — **no** Services/Grpc.
    2. Mark entry with stable `@[export lean_tee_guest_run]` (or Lean 4 export attribute of record for 4.32.1).
    3. Enforce purity: no `IO` in the call graph of the entry (CI grep / Lake check).
    4. Unit goldens: same vectors as today’s Rust twin / Lean tests (`action=vote.yes`, GuestProg v1/v2).

    B. C emission pipeline

    1. Lake target that builds the guest lib and retains/emits C under `.lake/build/ir/` (Lean already lowers to C).
    2. Script `scripts/sp1_lean_guest_build.sh`:

      3. - collect needed .c from guest modules + minimal runtime sources,

      - compile with SP1’s RISC-V clang (cargo prove / SP1 CC),

      - link into the SP1 guest crate as static lib liblean_tee_guest.a or compile Lean C directly into the guest build.rs.

      1. Pin toolchain: **Lean 4.32.1** (repo `lean-toolchain`) + SP1 **6.3.1** (current workspace). Document upgrade coupling.

      C. Minimal Lean runtime for SP1

      Hardest workstream. Pattern after Anoma’s RISC0 Lean runtime ideas, adapted to SP1:

      1. Inventory symbols required by emitted C for the phase-1 call graph (object allocator, RC, `ByteArray`, `String`, `Nat` ops used, panic/abort stubs).
      2. Provide SP1-safe stubs: no pthreads, no signals, no filesystem; abort → zkVM fail / deny output policy (choose fail-closed: commit `decision=deny` only if entry returns error code; panics should not be silent allow).
      3. Allocator: bump or RC heap in guest memory with fixed max (document limit; OOM → deny).
      4. Optional `LEAN_TEE_SEALED_*`-style hardening is N/A inside zkVM; focus on determinism and size.
      5. Deliverable: `host/lean_sp1_runtime/` (C/C++) + build instructions; **not** full Init.

      Risk: Lean runtime is large; phase 1 must aggressively limit imports so the link set stays small enough for SP1 execute/prove on reasonable hardware.

      D. SP1 guest crate rewire

      1. Replace `lean_tee_compliance::run_measured` in [`host/guest/src/main.rs`](host/guest/src/main.rs) with FFI call into Lean entry.
      2. Keep `sp1_zkvm::entrypoint!` / `io::read` / `commit_slice` in a **thin** Rust (or C) wrapper — allowed glue, not twin.
      3. Update `code_id` / registry: e.g. `lean-tee/compliance_operator/lean-sp1/v1` and `lean-tee/guest_prog_runtime/lean-sp1/v1` (or one ELF with two logical paths as today). **Measurement changes are breaking** for Strict allow-lists — version clearly; document migration from Rust-ELF measurements.
      4. `sp1_smoke` / careful scripts must use the new ELF.

      E. Host path during migration

      1. **Prove path:** SP1 guest = Lean-compiled only (goal).
      2. **Lean `teeServer` mock Prove:** can keep calling Lean oracles **in-process** (that *is* Lean, not a Rust twin) — preferred for mock.
      3. **Deprecate** Rust compliance as authoritative semantics; optionally keep for differential testing until parity is green, then delete from guest link and mark crate “host legacy / tests only.”

      TCB / refinement story (honest)

      Phase 1 refinement claim is pipeline trust, not a finished end-to-end theorem:

      • Trusted: Lean 4.32 compiler emit, minimal runtime, C/SP1 toolchain, SP1 prove/verify, shared hash.
      • Aspirational later: proofs that emitted C refines Lean IR; `sp1-lean` that SP1 chips refine Sail; optional CompCert-style story — **out of phase 1**.

      Do not market phase 1 as “formally verified Lean kernel on SP1.”

      Explicit non-goals (this plan)

      • Switching to RISC0.
      • Keeping Rust `lean_tee_compliance` as the SP1 semantic guest.
      • Full Lean elaborator/kernel in SP1 in phases 0–3.
      • Replacing `lean_tee_receipt` host verify with something else.

      Suggested branch / sequencing

      Work on confidentiality or a new branch lean-sp1-guest from development. Sequence: Phase 0 spike PR (prove feasibility) before large runtime investment; only then Phase 1–3.

      Success metric

      A third party can say: the measured SP1 guest ELF was produced from the Lean compliance/GuestProg sources we agreed, SP1 proves that ELF on public I/O, and Accept checks measurement + proof — with no Rust twin in the proven semantic loop.
