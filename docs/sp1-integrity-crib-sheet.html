How SP1 gives lean-tee integrity (plain English)

A short guide to what the SP1 proof is doing in lean-tee — for readers who are not cryptographers. Integrity of a public run, not a hardware secret vault.

One sentence

SP1 watches the agreed program run, builds a hard-to-forge certificate that that run really linked those inputs to those outputs, and lets anyone else check the certificate quickly — without keeping or replaying the full CPU worksheet.

1. The question SP1 answers

In lean-tee, SP1 is used for integrity:

Can we believe that this agreed program really ran on these public inputs and produced these public outputs?
Not Nitro confidentiality This is not “the host couldn’t see the data.” The proving machine can still see public inputs. For secrecy vs Nitro, see VS_NITRO.md.

2. Cast of characters

3. One job, step by step

Agree the program

Parties pin which software counts (logical codeHash, enforced inside the SP1 guest, plus published ELF / verifying-key digests). Analogy: agree which official calculator is allowed — not which buttons you’ll press later.

Run this job

The host feeds the guest three public stdin values:

#ValueMeaning
1config_hash32-byte digest of rules, or of GuestProg bytes
2inputse.g. action=vote.yes
3programGuestProg bytes, or empty → compliance path

Guest writes public outputs (e.g. decision=allow).

Record the worksheet (execution trace)

SP1 records a detailed execution trace: how the virtual CPU stepped from inputs to outputs. Different jobs → different traces. The trace is a temporary worksheet, not usually what you archive for audit.

Build the certificate (proof)

Using a proving key tied to that guest program, SP1 turns a valid worksheet into a small proof: “a correct run of this program on these inputs produced these outputs.”

  • Exam booklet = full trace (huge; discard after).
  • Sealed certificate = proof (compact; this is what travels).

The proof is a cryptographic object — not merely a hash of inputs‖outputs. Anyone can hash those; that would not prove a real run happened.

Check the certificate (verify)

With the public verifying key (vk), anyone checks the proof against the public values. lean-tee stores a receipt and often proof_ref = SHA-256 of the serialized proof (a handle for the proof blob).

agree program (ELF / vk) │ ▼ run guest on (config_hash, inputs, program) → outputs │ ▼ SP1 records valid execution trace (temporary) │ ▼ SP1 prove(proving key, run) → proof │ ▼ verify(vk, public values, proof) → accept / reject │ ▼ receipt + proof_ref (what counterparties keep)

4. What stays the same vs what changes

Stable (identity)Per job (this run)
Guest ELF / verifying key Execution trace
Logical codeHash / operator id Inputs, outputs, proof, proof_ref

Program identity is stable. Each proof is about one specific run.

5. Why a fake story fails

An adversary can invent any fake trace they like. They generally cannot turn it into a proof that verifies under your vk unless a real run of that ELF could produce those public I/O (assuming SP1 soundness).

Intuition:

  • Valid run → worksheet obeys CPU/program rules → proof can verify.
  • Made-up worksheet → rules don’t hold → prove fails or verify rejects.
  • Forging a verifying proof anyway ≈ breaking the crypto (like forging a signature).

Counterparties don’t need the trace. Verification of the proof replaces re-checking the worksheet. Auditors keep the receipt / proof, not the megabyte CPU dump.

6. Glossary

TermPlain meaning
ELF The guest binary that actually runs in SP1 (lean_tee_guest_lean).
Trace Step-by-step record of one run. Witness for proving; usually discarded after.
Proving key (pk) Secret-ish setup material used to create proofs for that ELF.
Verifying key (vk) Public material used to check proofs for that ELF.
Proof Compact certificate that a valid run of that program produced the claimed I/O.
Soundness Fake / invalid runs shouldn’t yield a proof that verifies (except negligible chance).
proof_ref In lean-tee: hash of the serialized proof — a receipt handle, not the proof math itself.
Measurement Wire fields codeHash + configHash (logical identity + rules/program digest).

7. What this is not

  • Not a guarantee the host will always cooperate (it can refuse to prove).
  • Not confidentiality against the proving machine.
  • Not “the same CPU trace every time” — only the same program.
  • Not something the guest Lean code constructs; SP1 on the host does.
