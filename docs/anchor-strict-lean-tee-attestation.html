1. The problem Strict Mode solves

In Anchor Chain, many compliance decisions happen off-ledger: an agent (or node operator) runs local logic—“may this participant cast?”, “is this trade side allowed?”—and later posts an on-ledger message such as CastVote or SubmitSide.

Classic Mode proves properties of the on-ledger agreement. It does not, by itself, prove that the off-ledger gate was the agreed measured program rather than a compromised host agent that always returns decision=allow.

Strict Mode (opt-in) closes that gap for designated interactions: before (or as a prerequisite to) the sensitive act, the participant must register compliance evidence whose core is a lean-tee TeeReceipt. Counterparties and the Anchor node verify that receipt against an agreed measurement policy—without needing an identical TEE on every verifier’s laptop.

2. What lean-tee is (and is not) in this story

lean-tee is an integrity-first attestation stack for public inputs and outputs:

  • A registered guest (e.g. compliance_operator, voting_operator) is identified by a measurement codeHash = SHA256(code_id).
  • Rules / config bytes are hashed into configHash.
  • Public I/O is bound into resultHash (the Anchor evidence_root_hex).
  • A proof_ref is either a mock digest (CI/demo) or an SP1 zkVM proof commitment (production integrity profile).
Not AWS Nitro confidentiality lean-tee does not seal secrets from the host OS. It answers: “did this measured guest run on these public inputs and produce these outputs?”—not “did the host fail to read memory?” Hardware enclaves remain a separate compose path when secrecy is required.

Important nuance for Lean: the specification of the compliance operator lives in Lean (and a Rust host twin for mock/parity). Under SP1, the executable guest is the Lean-compiled RISC-V ELF lean_tee_guest_lean, whose behaviour is intended to match that spec. Counterparties agree on the logical measurement (codeHash) and, for lean-tee-v2, the published ELF / verifying-key digests—not on “upload Lean source into the zkVM.”

5. What the verifying party checks (no twin TEE required)

A counterparty or the Anchor node does not need to re-run the compliance operator inside an identical TEE. They verify evidence:

  1. Profile / suite — interaction declared lean-tee-v1 or v2; suite fail-closed if unknown.
  2. Measurement — codeHash / configHash match the policy for this Strict interaction (agreed guest + rules digest).
  3. resultHash — recompute SHA256(len-prefixed(domain, codeHash, configHash, inputs, outputs, nonce)) and compare to evidence_root_hex.
  4. Proof — for v1, recompute mock proof_ref via lean_tee_receipt; for v2, host-verify SP1 (production path; Anchor wiring may still be catching up to full SP1 verify).
  5. Binding — attested action / interaction in public inputs must match the ballot/trade and the later act; OrgCompliance Lean source must embed the evidence root / code hash as required by Anchor checks.
Portable verify This is the point of lean-tee relative to Nitro-rooted attestation: CI machines, other clouds, and chain nodes can Accept using shared algorithms and allow-lists—without AWS PCR trust or a local enclave clone.

6. Profiles: mock vs SP1

ProfileMeaning for Anchor StrictUse
lean-tee-v1 Mock proof digest; Anchor node verifies via lean_tee_receipt Demos / CI only—not production integrity
lean-tee-v2 SP1 Hypercube proof of the RISC-V guest execution; never trust client proof_ok alone Production integrity target

SP1 adds a cryptographic claim that the measured guest ELF produced the public outputs from the public inputs. Counterparties should pin that ELF via the published digests artifact (not via folding ELF bytes into wire codeHash). SP1 does not make the third-party host confidential, and it does not force the host to cooperate (censorship remains possible).

7. Implications of an adversarial third-party node

Assume the adversary controls the machine that was supposed to run lean-tee / the agent.

What they can do

  • Refuse to attest — never call Execute / never RegisterCompliance. Strict act gates then block their CastVote / SubmitSide.
  • Selective honesty — only prove runs that favour them (if those runs are real under the guest). SP1 / mock both allow “choose which true executions to publish.”
  • Under mock (v1) — if they also control receipt production and verifiers only check mock algorithms, a sophisticated adversary who can forge a consistent mock digest for false I/O is in scope for “don’t use v1 in production.” Treat v1 as demo-grade.
  • Under SP1 (v2), soundness assumed — they generally cannot forge a verifying proof that guest G on inputs I produced outputs O unless that execution occurred. They can still run the real guest on adversarial-chosen public inputs that the policy still allows.
  • Wrong guest / wrong rules — only works if verifiers’ measurement allow-list is weak or missing. Strict Mode’s value depends on pinning codeHash / configHash.
  • Replay — attempt to reuse an old receipt on a new ballot; binding interaction= and Anchor’s registration checks are meant to stop this.
  • Local confidentiality mode (if used) — does not stop local root from reading worker memory; it only keeps secrets out of the public receipt surface.

What honest counterparties gain

  • Cheap reject of forged or inconsistent receipts (strict_attestation_fail in demos when evidence_root_hex is mangled).
  • Policy-locked guest identity — “this node claims the agreed voting operator measurement,” not an arbitrary binary.
  • Interaction-bound decisions — attested action tied to the ballot / trade id before the ledger act.
Not a silver bullet An adversarial node that never produces a valid attestation is simply locked out of Strict acts—not magically forced to behave. An adversarial node that produces a valid attestation of an undesirable but policy-allowed decision has proven that the agreed guest allowed it; governance must tighten rules / guests, not expect the TEE to invent policy.

8. Can adversarial transactions be rejected before they are added to the chain?

Yes—for Strict-gated acts, that is the design intent of the Anchor node path.

In the reference anchor-node implementation, Strict Mode is enforced when handling messages such as RegisterCompliance, CastVote, and SubmitSide:

  1. At registration — if the ballot/trade is Strict for that participant, missing or invalid lean-tee fields → failure (strict_attestation_fail). The attestation is not accepted into node state.
  2. At the act — e.g. SubmitSide / CastVote checks that a Strict attestation is already registered for the sender on that interaction. If not → reject with detail such as strict attestation required before SubmitSide (before applying the state transition that would count as “the transaction succeeded on the ledger.”
“Before the blockchain” in practice Rejection happens in the node’s transaction / message validation path (precheck / verify / apply gate)—i.e. the adversarial message does not become an accepted Strict act in ledger state. Demos assert forged evidence roots fail at this layer.

Nuances that matter operationally:

  • Validation vs gossip — a malicious peer might still broadcast a bad message; honest nodes that enforce Strict simply do not accept it into state. Network-level spam is a separate DoS concern.
  • Classic Mode — interactions not opened as Strict do not get this gate; Classic demos remain unchanged by design.
  • Consensus / multi-node — every validating node (or the relevant quorum rules) must apply the same Strict checks. If a Byzantine minority skips checks, that is a node-policy / consensus problem, not a lean-tee crypto failure.
  • Timing — attestation is registered first; the later act is gated. The “transaction” that is rejected is the unauthorized cast/submit (and/or the bad RegisterCompliance), not “after finality of a successful Strict act.”

So: yes, Strict Mode is specifically there so adversarial or unattested attempts can be rejected in validation before they become accepted on-ledger Strict actions—provided the deployment actually runs those gates.

9. Limits and honesty checklist

  • lean-tee Strict attestation is integrity of public compute, not confidentiality.
  • Verifiers need the agreed measurement policy and profile—not a twin enclave.
  • lean-tee-v1 is for demos; production integrity aims at lean-tee-v2 with real SP1 host verify.
  • Host censorship and selective disclosure remain possible.
  • Optional local sealed-worker confidentiality ≠ Nitro; do not market it as such.
  • Lean specifies the operator; SP1 executes the measured Lean-compiled guest—not Lean kernel on RISC-V.
